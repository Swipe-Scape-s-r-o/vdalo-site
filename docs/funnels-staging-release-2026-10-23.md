## Що змінено

- Зібрано hero в цілісну композицію тексту, CTA та медіа, окремо для desktop і mobile.
- Оформлено нижню частину всіх 13 сторінок: тематичні переваги, три кроки після заявки, FAQ, тариф/завершальний CTA та футер.
- Для кожного лендоса підготовлено окремі тематичні тексти переваг.
- За новою вказівкою власника /q3 збирає заявки на автоматизацію туристичного збору після реєстрації та налаштування об’єкта. Калькулятор, його поля та клієнтський запит до API розрахунку видалено з цієї воронки. Окремі публічні калькулятори сайту не змінено.
- /qc отримав наочний опис шляху гостя до прямого бронювання замість повторення H1 на брендовій заглушці.
- /q6 і /q9 отримали читабельний табличний приклад календаря з явною позначкою вигаданих даних.
- /q7: точні повідомлення помилок, дробові суми/відсотки, очищення застарілого розрахунку та подія завершеного редагування без події на кожне натискання клавіші.
- У формі приховано honeypot від допоміжних технологій, додано маскування полів для Clarity, підтримку Enter на першому кроці та захист від одночасного повторного надсилання.
- /qd: умови організації ключа або іншого доступу пояснено в основній пропозиції.
- /q4, /q5, /qb: додано пояснення відмінності узгоджених сценаріїв відповідей від гостьового AI-помічника у розробці. Фактичний продуктовий бекенд цим оновленням не перевірявся.
- Додано місток спеціальних подій до вже підключеного Google tag. Параметри GA4 мають явний дозволений перелік без контактів, персональної мітки t та вільних відповідей. Localhost не відправляє їх до GA4; staging позначає debug_mode. Не слід паралельно дублювати ці події GA4 event-тегом у GTM.

## Локальні перевірки

- 170 автоматизованих тестів: успішно. Тести заявки використовують підставний одержувач, без реального зовнішнього надсилання.
- Валідація schema: 90/90 маршрутів, 0 помилок.
- У Chrome переглянуто всі 13 маршрутів на desktop 1440 CSS px і mobile 390 CSS px, збережено повні скриншоти у docs/design-references/oct23.
- Додатково перевірено геометрію всіх 13 сторінок на 320 і 768 CSS px. Горизонтального переповнення основного вмісту не знайдено.
- Масштаб користувацького Chrome становив 67%; розмір override підбирався за фактичним window.innerWidth, а не лише за аргументом інструмента.
- /q3: у DOM немає tax-inputs, конфігурація не містить громад для розрахунку, дві CTA відкривають спільну контактну форму. Доставлення заявки ще потребує наскрізного тесту.
- Знімки до зміни та первинний production-аудит збережені окремо.

## Перевірки staging

Статус: очікується публікація staging та повторна перевірка нового вмісту. Результати будуть доповнені після фактичного browser pass.

## Межі й окремі дії перед production

- Реальні заявки не надсилати без погодженого тестового одержувача. Наявність форми та локальний mock-тест не підтверджують доставлення до CRM.
- Залишається окремий GTM/Clarity-крок: початковий аудит виявив пряме підключення Clarity та офіційний GTM-тег одночасно. Потрібно залишити один спосіб і перевірити матрицю згоди. Публікація загального контейнера впливає на production; її слід узгодити з завершенням staging-релізу.
- Фактичне отримання нових GA4-подій потрібно підтвердити в DebugView/Tag Assistant після staging, окремо від перевірки вихідного коду.
- Фізичні iOS/Android та інші браузери не замінюються перевіркою viewport у Chrome.
- Юридичний футер головної та персональні реквізити не змінено. Значення до звіту не копіювалися.
- Файли deploy/, серверні налаштування, схема бази даних і зв’язок CRM не змінювалися.
