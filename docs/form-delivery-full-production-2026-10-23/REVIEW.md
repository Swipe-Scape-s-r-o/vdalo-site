# Повний прогін форм на основному сайті

Власник попросив окремо перевірити всі форми на production. Контакт для тестів погоджений раніше; використовується лише під час введення, не зберігається в репозиторії. Назви тестів мають префікс `ТЕСТ VDALO QA`, об’єкти не підключати.

## Початкові результати

- Повторний read-only інвентар: 177 маршрутів, очікувані поля 298 form-елементів збігаються, 18 JS доступні. Платіжні форми й калькулятори не трактуємо як CRM-заявки.
- Усі 13 нових лендосів /q1–/q9, /qa–/qd: окрема реальна відправка кожної форми через браузер, явне підтвердження приймання й UI успіху.
- Усі 8 старих пропозицій: /audit, /research, /trial, /switch, /one-process, /pms-check, /founding-hotels, /hotel-research — окрема реальна відправка кожної, приймання підтверджене. Для опитування перевірено добровільний контакт з окремою згодою на дослідницьке інтерв’ю.
- Повідомлення про успіх означає явне `{ok:true}` серверного приймача. Доставка кожної з цих окремих заявок у Telegram та відображення колонок CRM без доступу до цих систем не стверджуються. Раніше власник підтвердив отримання нової /q9 через цей канал.

## Знайдений дефект /tourist-tax/start

- P1: коректний телефон відхиляється клієнтом. У згенерованому inline-JS регулярні вирази втрачають зворотні слеші: `/D/` та `[+()ds.-]` замість `\D`, `\d`, `\s`.
- P1: навіть після клієнтської перевірки старий короткий запит має лише телефон, опціональні об’єкт і місто, а спільний обробник вимагає email, ім’я, тип і кількість номерів, яких немає у цій формі.
- Виправлення: `String.raw` для inline-JS; явне підтвердження `ok:true`; стабільний ID повтору; маскування форми; окремо розпізнані лише два точні телефонні варіанти tax-docs/tax-report з funnel=tourist_tax, source=website. Повні нові форми й trial зберігають свої обов’язкові поля.
- Приймач залишається наявним авторизованим CRM-каналом. Для телефонної консультації не вигадується email чи ім’я.
- Регресія: 6 нових тестів перевіряють згенеровані regex, обидва варіанти через старий CRM parser, мінімальну форму, повтор, згоду, неправильні поля та відмову приймача. Повний набір: 212/212.

Наступні кроки: staging → UI та валідація → production → реальне приймання телефонної консультації; продовжити перевірку решти спільних форм. Серверні налаштування й секрети не змінюємо.
