# Відновлення заявок через старий CRM-приймач

23.10.2026. Власник попросив відновити попередній шлях: сайт → внутрішня CRM → Telegram, далі ручне підключення об’єкта. Доступу до Hetzner немає; конфігурацію сервера й секрети не змінюємо.

## Доведена причина

- Production `/api/funnel/leads`: позначена заявка audit повернула 200, ok:true, leadId. Власник підтвердив отримання у Telegram.
- Production `/api/leads/audit`: позначена callback-заявка повернула 200, ok:true.
- Production `/api/funnels/top5`, новий q9: позначена заявка повернула 502, ok:false.
- Старий приймач платформи (`site-intake.ts`, локальний snapshot 226bc51) розуміє vdalo-website, vdalo-microlandings і vdalo-top5-funnels. Новий vdalo-robot-funnels не розуміє. Крім того, Idempotency-Key повинен дорівнювати id/lead_id у тілі. Нові форми надсилали складений ключ із двокрапками, тому старий приймач відхиляв його.
- Скріншот 503 означає відсутній для конкретного середовища/форми endpoint. На поточному production q9 відтворено саме 502; ці причини не ототожнюємо.

## Виправлення

- Нові 13 лендосів адаптуються до старого vdalo-microlandings. Зберігаються ім’я, об’єкт, основний телефон, вид запиту, сторінка й UTM.
- Email та спосіб зв’язку показуються також у тексті заявки. Повний структурований пакет контактів, відповідей, калькулятора й Callo-атрибуції зберігається у підтримуваному старим приймачем qualification.quiz_answers.form_fields. У GA4/Clarity ці контакти не передаються.
- Обидва кроки /go/trial залишаються окремими ідемпотентними подіями; email та телефон надходять у старому top5-контракті, тому події можуть доповнювати ту саму CRM-картку за email. Повтор тієї самої події використовує той самий ключ; нові доповнення не відкидаються як дубль першого кроку.
- Для callback/audit/trial головного сайту збережено старий контракт; додані контакти й контекст відображаються в timeline через estimate.
- Endpoint і токен беруться тільки з наявного серверного env; при відсутності спеціалізованого endpoint можна використати старий загальний канал. Ніяких нових секретів у Git чи браузері.
- HTTP 200 з ok:false чи сторінкою HTML не вважається успіхом. Приймання має явно підтвердити ok:true.
- Повтор після помилки на нових лендосах та головних формах не створює новий випадковий submission ID при незмінених даних.
- Обчислені значення комісійного калькулятора більше не губляться через очищення вкладеного answers.calculator.

## Перевірки до staging

- 206/206 тестів, включно з 21 новим. Контракти проходять через snapshot реального старого parser, а не mock, який приймає будь-яке тіло.
- Усі 13 маршрутів: ім’я, об’єкт, контакти, email у timeline, UTM, спосіб/час зв’язку, відповіді й Callo-мітка. Окремо — main callback/audit/trial, два етапи email-форми, повтор, відмова, не-JSON, згода та невалідні поля.
- Schema: 91/91, 0 помилок.
- Інвентар: 177 публічних маршрутів, 173 з формами, 298 form-елементів (включно з повторюваними глобальними діалогами, калькуляторами та оплатою); HTTP-помилок рендеру немає. Це інвентар, не твердження про 298 реальних відправок.
- Локальний browser preview недоступний із браузерів цього ПК через мережу. Локальні тести контрактів пройшли; browser acceptance завершуємо на staging.

## Межі старого приймача

- Старий microlanding reader має одне основне поле phone_or_email. Для нових лендосів основним є телефон, email видно в тексті заявки. Пакет містить обидва контакти; окреме автоматичне заповнення колонки email потребуватиме оновлення приймача платформи.
- У старому top5 reader ім’я не переноситься в основну колонку CRM, хоча новий повний snapshot його зберігає у внутрішньому рядку заявки. Ця частина його UI не виправляється кодом сайту. Саме тому не стверджуємо, що кожне нове поле стало окремою колонкою старої CRM.
- PMS-чекліст надсилає користувачу звіт через Resend; це окрема функція, яка історично не створювала CRM-заявку. Оплата, QR-генератор і розрахункові форми не перетворюються на заявки.
- Створення компанії, tenant і облікового запису не виконується: лише NEW-заявка для ручного онбордингу.

## Browser acceptance на staging

- Виправлення c1617aa опубліковане на staging; браузер отримує robot-funnels.js?v=20261023f.
- Усі 13 маршрутів /q1–/q9, /qa–/qd перевірені в Chrome на ширинах 390 і 1440 px. Перевірені відкриття/закриття діалогу, обидва кроки, обов’язковість назви об’єкта, імені, email, телефону й згоди. Порожня форма не показує успіх; горизонтального переповнення немає. Результати: staging-mobile.json і staging-desktop.json.
- Позначена справжня відправка /q9 на staging повернула 503: у серверному середовищі не задано канал приймання. Стара форма /audit на тому самому staging має data-ready=false. Це відсутність серверного env, а не доказ відмови CRM від виправленого формату.
- Повна доставка staging → CRM → Telegram НЕ підтверджена: на staging немає налаштованого каналу. Захист staging і серверні секрети не змінювалися.
- На поточному production без нових відправлень додатково перевірені валідація першого кроку /go/trial та головної контактної форми. Порожні контакти не надсилаються. Старий /audit доступний з активною формою; його реальне отримання Telegram уже підтвердив власник.

## Публікація

Код і browser acceptance підготовлені на staging. Наступний крок — перегляд власником і погодження staging → main за AGENTS.md. Production у цьому виправленні ще не змінювався. Після релізу потрібна одна позначена заявка нової форми /q9 через наявний production-канал та підтвердження її отримання власником; успіх локальних тестів і UI не замінює цю перевірку.
