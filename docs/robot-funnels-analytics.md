# Аналітика сторінок робот-дзвінка VDALO

## Що вже працює в коді

- Спільний сервер додає контейнер Google Tag Manager `GTM-PKDT7MMT` до HTML сторінок. Це підтверджує лише наявність контейнера в коді сайту; конфігурацію GA4 усередині GTM треба перевірити в самому акаунті.
- Тринадцять сторінок воронок (`/q1`, `/q1b`, `/q2`…`/q10`) передають події в `window.dataLayer`.
- Кожна подія воронки має `brand`, `code`, `funnel`, `page_format`, `page_path`, `page_title` і `utm_content`.
- Clarity підключена спільним consent-скриптом, але завантажується тільки після згоди відвідувача на аналітичні cookie. Після відмови сесія не записується. Записи Clarity треба перевірити на опублікованому домені після згоди.
- Заявка `lead_success` надсилається в `dataLayer` лише після успішної відповіді сервера. `form_submit` — це спроба, а не гарантовано отримана заявка.

## Події для GTM та GA4

| Подія в `dataLayer` | Значення | Рекомендоване використання |
|---|---|---|
| `lp_view` | Завантажилась сторінка воронки | Діагностика воронки. Не створювати з неї ще один `page_view` у GA4. |
| `cta_click` | Натиснули CTA; `place` = `hero` або `bottom` | Взаємодія з основним CTA. |
| `form_open` | Відкрили форму | Перехід від перегляду до форми. |
| `form_step1_done` | Пройшли перший крок | Без назви об’єкта чи відповідей. |
| `form_step2_view` | Побачили крок контактів | Воронка форми. |
| `form_submit` | Надіслали форму | Спроба; окремо відстежувати помилки та успіх. |
| `lead_success` | Сервер підтвердив отримання | Основна конверсія для запиту на тест. |
| `lead_error` | Сервер не підтвердив заявку | Діагностика помилок без тексту введення. |
| `video_start`, `video_25`, `video_50`, `video_75`, `video_complete` | Перегляд відео та прогрес | Аналіз залучення; є безпечні ідентифікатори відео й варіанта. |
| `questions_done` | Дали відповіді на інтерактивні питання | Передається лише кількість відповідей, не їхній зміст. |
| `calc_result` | Успішно виконано розрахунок турзбору | Передається тільки тип калькулятора, без громади, сум, ночей чи кількості гостей. |
| `faq_open` | Відкрили питання FAQ | `index` — позиція питання на сторінці. |

У GA4 налаштувати Custom Event triggers за точним значенням `event` та окремі GA4 Event tags. Для конверсії позначити `lead_success` як key event. `lp_view` залишити звичайною подією. Перевірити, що на всіх маршрутах вже є рівно один GA4 `page_view` від основного Google tag / GA4 config. Якщо його там немає, налаштувати один тег на All Pages; не перетворювати `lp_view` на другий `page_view`.

Для розрізів у GA4 достатньо зареєструвати event-scoped custom dimensions: `code`, `funnel`, `page_format`, `page_path`, `page_title`, `utm_content`, `place` (для `cta_click`), `video`, `video_variant`, `watched`, `answer_count`, `calculator_type`, `index`. Перед реєстрацією переглянути актуальну конфігурацію, щоб не створювати дублікати. Не реєструвати поля форми як параметри.

## Приватність

Не надсилати в GA4 або Clarity ім’я, email, телефон, назву об’єкта, назву PMS, відповіді квізу, значення калькуляторів, Callo-мітку `t`, повний текст помилки чи інші поля заявки. Параметр `t` є вхідною CRM-атрибуцією і відсутній у custom events, але стандартний GA4 `page_view` може зібрати повну URL-адресу. У GTM передавати `page_location` без `t` (та інших неаналітичних параметрів запиту), зберігаючи лише потрібні UTM-мітки; також перевірити авто-вимірювання і фільтри URL, щоб у URL не потрапляли персональні дані. На поточному етапі до `dataLayer` передаються лише маршрут і заголовок сторінки для контексту; введені відповіді для діагностики обробляються в браузері, але не включені в події аналітики.

Переконатися, що Clarity маскує поля введення, і що згода на Clarity зберігається окремо від необхідних cookie. Наявність GTM сама по собі не доводить коректне налаштування consent mode для тегів Google: перевірити згоду для GA4 у GTM окремо, відповідно до налаштувань приватності сайту.

## Після деплою

1. У GTM Preview відкрити кожний маршрут воронки й перевірити `lp_view`, `page_path`, правильний `code` та відсутність дублів тегів.
2. Пройти CTA та форму до тестової успішної відповіді API. Перевірити, що `lead_success` іде лише після серверного успіху; помилкова відповідь породжує тільки `lead_error`.
3. Відкрити GA4 DebugView та перевірити page views і custom events. Надіслати один тестовий лід з тестовими даними, потім видалити/позначити його в CRM згідно з процесом команди.
4. Відкрити сайт без вибору cookie та перевірити, що Clarity не завантажується. Дати згоду, відкрити окрему воронку, натиснути CTA й перевірити Clarity Live/Recordings. Також перевірити відмову і зміну вибору.
5. Повторити на телефоні та desktop для всіх 13 маршрутів через матрицю: перегляд, CTA, форма, відео/інтерактив сторінки, успіх/помилка.

GTM Preview, GA4 DebugView і Clarity Recordings залежать від опублікованого домену, доступів до відповідних акаунтів і фактичної конфігурації контейнера. Підготовку в коді й план перевірок можна завершити до деплою; остаточну перевірку збору даних — після нього.
